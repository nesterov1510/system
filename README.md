# MSB

Собственная система приёмки и ремонта техники для сервисного центра
**(полный редизайн: новый интерфейс, бренд MSB)**.
**Без Bitrix / amoCRM / 1С как ядра** — свой backend (FastAPI), своя БД
(PostgreSQL), свой UI (Jinja2 + HTMX).

> ✨ **MSB** () — современный дизайн: адаптивная доска
> ремонтов, карточки со статусами, мастер приёмки в 3 шага, касса, склад,
> статистика, чат и печать — всё в едином фирменном стиле.

> 🌍 **Регион: Туркменистан** — город Ашхабад (Asia/Ashgabat), телефоны +993,
> **валюта — туркменский манат (TMT, «ман.»)**. Цены, статистика и печать
> заточены под туркменский регион.

> Статус: **MVP (0–6) + склад + оплаты/касса + тесты** готовы.
> Работают: форма приёмки с прайс-подсказкой, карточка ремонта
> (timeline/фото/комментарии/запчасти/**оплата**), печать с редактором шаблона бланка,
> публичная QR-страница, доска ремонтов, очередь call-центра, прайс API, дашборд
> «курс ремонта» + AI-прогноз ETA, склад (запчасти + купленная техника с
> статусами разборки), **касса** (платежи/методы/выручка),
> SMS-уведомление о готовности и ежедневные
> напоминания «заберите технику», **279 pytest-тестов**.

## Приёмка без аккаунта (`/intake`)

Приёмка для тех, у кого нет учётки: планшет на стойке, точка приёма, филиал.
Вход не требуется. Страница устроена **ровно как обычная приёмка сотрудника**:
сначала выбор типа техники, затем та же карточка с полями клиента, техники,
комплектации, состояния, неисправности, доставки и фото. Отличие одно —
нельзя выбрать мастера.

* Ремонт создаётся в статусе **«Новый»** и попадает в общий список «Все ремонты».
* Мастер на ней **не назначается**: ремонт берёт свободный мастер
  («Взять в работу» в карточке) либо назначает администратор.
* Принявшим сотрудником указывается служебная учётка **«Приёмка без аккаунта»**
  (`intake@msb.local`) — в списке и журнале видно, откуда запись. Войти под ней
  нельзя: учётка выключена, а пароль случаен.
* Правила те же, что и на приёмке сотрудника: телефон `+993` + код оператора
  (`12, 60–65, 71, 72`) + 6 цифр, марка/модель/SN заглавными, комплектация и
  состояние, фото при приёмке, автопечать по общей настройке.
* Обе страницы рендерит один шаблон (`repairs/new.html`), поэтому форма не
  разъедется со временем. Разбор полей — общий (`app/webui/intake_form.py`).
* Поиск по базе клиентов (автоподстановка имени и телефона) на публичной
  странице выключен: анонимный доступ к контактам заказчиков недопустим.
* После оформления показывается номер ремонта и ссылка на страницу статуса
  `/r/{token}` — ту же, куда ведёт QR на бланке.

Включается и настраивается в **«Админ → Настройки → Приёмка без аккаунта»**:
там же задаётся необязательный код доступа (с кодом страница открывается по
`/intake?key=КОД`).

## Сценарий «приёмка → печать → QR → чат» (curl)

```bash
# 1. Логин
TOKEN=$(curl -s -X POST localhost:8085/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"admin@msb.local","password":"admin123"}' \
  | python3 -c "import sys,json;print(json.load(sys.stdin)['access_token'])")

# 2. Город (сидируется "Ашхабад", slug=asg, Asia/Ashgabat)
CITY=$(curl -s localhost:8085/api/admin/cities -H "Authorization: Bearer $TOKEN" \
  | python3 -c "import sys,json;print(json.load(sys.stdin)[0]['id'])")

# 3. Приёмка (Idempotency-Key защищает от дублей)
curl -s -X POST localhost:8085/api/repairs \
  -H "Authorization: Bearer $TOKEN" \
  -H "Idempotency-Key: $(uuidgen)" \
  -H 'Content-Type: application/json' \
  -d "{\"city_id\":\"$CITY\",\"client\":{\"full_name\":\"Иванов Иван\",\"phone\":\"+993 61 123456\",\"consent_pdn\":true,\"consent_storage\":true},\"device_type\":\"Телевизоры\",\"brand\":\"Samsung\",\"model\":\"UE55\",\"fault_client\":\"не включается\"}"

# → номер TV-ASG-2026-00001, public_token, storage_until = +3 месяца
# телефон нормализуется к 99361123456 — один и тот же человек, записанный
# как «8 61 123456», «+99361123456» или «61123456», остаётся одним клиентом

# 4. Публичная страница по QR-токену
curl -s localhost:8085/api/public/r/{public_token}

# 5. Печать бланка (PDF A4)
curl -s -X POST localhost:8085/api/repairs/{repair_id}/print \
  -H "Authorization: Bearer $TOKEN"

# 6. Чат с упоминанием ремонта
CH=$(curl -s localhost:8085/api/chat/channels -H "Authorization: Bearer $TOKEN" \
  | python3 -c "import sys,json;print(json.load(sys.stdin)[0]['id'])")
curl -s -X POST localhost:8085/api/chat/channels/$CH/messages \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"text":"Принято #TV-ASG-00001"}'
```

## Печать (Epson EcoTank L3250)

L3250 — **струйный A4** принтер, он **не поддерживает ESC/POS**. Бланк
печатается как PDF через драйвер ОС. Схема:

```
API рендерит PDF (кириллица) → print_jobs(queued) → print-agent забирает
→ печать через системную команду → статус done/failed + audit
```

**Запуск print-agent** на сервере MSB (там же, где CUPS):

```bash
cd apps/print-agent
pip install -r requirements.txt
MSB_API_URL=http://<api-host>:8085 \
MSB_EMAIL=admin@msb.local \
MSB_PASSWORD=admin123 \
python agent.py
```

Бланки A4 печатаются в локальную очередь CUPS (`cups_local`): агент сам
выполняет `lp -d office_printer_a4 <бланк.pdf>`, дополнительная команда печати
не нужна. Этикетки уходят **напрямую по сети** в raw-принтер TSPL
(`raw_tspl`, `192.168.8.75:9100`) — см. ниже. `MSB_PRINT_CMD` нужна только для
режима `agent` (печать драйвером ОС, например SumatraPDF на Windows):
- **Linux/CUPS:** `lp -d ИМЯ_ОЧЕРЕДИ {file}`
- **Windows:** `powershell -Command "Start-Process -FilePath '{file}' -Verb Print"`
- **macOS:** `lp -d ИМЯ_ОЧЕРЕДИ {file}`

**Тип техники — в правом верхнем углу бланка.** Класс, выбранный на приёмке
(«Телевизоры», «Мониторы», …), печатается отдельной строкой в рамке справа от
номера ремонта, а в поле `M_Model` остаются только марка и модель. Доставка
(район + необязательный комментарий из приёмки) попадает в блок `Görkezme`
строкой `Eltip bermeli: …`.

### Принтеры: бланки в CUPS, этикетки — raw TSPL

Настройка — в админке (`Админ → Настройки → Принтер`), для каждого принтера
своя карточка и своя кнопка тестовой печати:

| Что печатаем | Куда | Режим |
|---|---|---|
| Бланки приёмки A4 | очередь CUPS `office_printer_a4` | `cups_local` |
| Этикетки 58×38 мм | `192.168.8.75:9100` (TSPL) | `raw_tspl` |

Режимы бланков A4:

- **`cups_local`** (по умолчанию) — очередь в CUPS на этом сервере, нужен только `lpstat -p`-имя очереди;
- **`cups_remote`** — очередь расшарена CUPS на другом компьютере (IP + порт 631);
- **`agent`** — печать драйвером ОС (Windows/SumatraPDF, `MSB_PRINT_CMD`);
- **`ipp`** — прямая печать по IP через AirPrint/IPP (порт 631).

Режимы этикеток: **`raw_tspl`** (по умолчанию, напрямую в 9100), `cups_local`,
`cups_remote` — если термопринтер всё же подключён к CUPS.

Адрес raw-принтера этикеток по умолчанию задаётся env `MSB_LABEL_HOST` /
`MSB_LABEL_PORT` (`192.168.8.75` / `9100`); имя очереди A4 — `MSB_PRINTER_A4`.

### Этикетки ремонта 58×38 мм

Принтер этикеток не в CUPS: он слушает `192.168.8.75:9100` и читает TSPL,
поэтому MSB собирает этикетку в монохромный растр 203 dpi и шлёт её командой
`BITMAP` напрямую (кириллица — из DejaVu Sans, QR — из qrcode). Этикетка на
технику: ФИО и телефон клиента, номер ремонта, комплектация и дефекты, QR на
закрытую карточку мастера. Этикетка клиенту: номер и QR на публичную страницу
`/r/{token}`. Настройка и диагностика — в [`LABEL_PRINTER.md`](LABEL_PRINTER.md).

## Статусы ремонта: их пять, остальное — в полях

Статус описывает только этап работы. Факты «технику забрали», «ремонт готов, но
техника стоит в сервисе» статусами больше не считаются — они выводятся из дат
ремонта (`RepairStatus` в `app/db/models.py`):

| Статус | Когда |
|---|---|
| `Новый` | приняли, исполнитель ещё не назначен |
| `На диагностике` | есть исполнитель, диагностика |
| `В работе` | ремонтируем (сюда же ушло старое «Согласование») |
| `Ждёт запчастей` | ждём деталь |
| `Завершён` | ремонт закончен (`ready_at`), дальше смотрим на `issued_at` |

| Факт | Как определяется | Где видно |
|---|---|---|
| Готово, но техника в сервисе | `ready_at` заполнен, `issued_at` пустой | жёлтая строка в списке по кнопке «⏳ Готово, но в сервисе» |
| Клиент забрал технику | `issued_at` заполнен (кнопка «📦 Выдано клиенту», `POST /api/repairs/{id}/issue`) | чип «✓ выдано» в карточке и в колонке «🏁 Итог» |
| Забрал, но не оплатил | `issued_at` заполнен и нет отметки об оплате/платежей | красная строка в списке — подсветка включена всегда |

Старые десять статусов переносит миграция данных `repair_statuses_v2`
(`app/db/datamigrate.py`): «Выдано» дополнительно проставляет `issued_at`,
у завершённых без `ready_at` появляется дата приёмки, а сохранённый в настройках
список статусов заменяется актуальным. API старые строки больше не принимает
(422), а в интерфейсе приводит их к новым (`map_status()`).

## Список «Все ремонты» и права мастера

Мастер видит **только свои ремонты и свободные** — свободные затем, чтобы взять
заказ себе. Старшие роли (администратор, оператор, менеджер) видят всё.

**Свои** — где он исполнитель (назначен напрямую через `master_id` или через
список исполнителей `repair_masters`, в том числе как помощник), **а также
собственная приёмка — но только пока исполнитель не назначен**. С назначением
исполнителя заказ становится заказом исполнителя: у приёмщика он уже не «свой»
(та же граница, что у права печати своей приёмки).

**Свободные** — исполнитель не назначен, принял не мастер (приёмка
оператора/админа или публичной приёмки, ушедшая в общую очередь), и ремонт ещё
не завершён и не выдан.

Что мастеру **не** видно:

- чужие ремонты с назначенным исполнителем — в том числе те, что он сам принял
  при приёмке, но передал другому мастеру;
- **чужая приёмка без исполнителя** — её принял другой мастер, она уже занята им
  (он же печатает на неё этикетку), поэтому «свободной» она не считается;
- завершённые и выданные ремонты без исполнителя — брать там нечего.

Границы заданы один раз в `app/services/repair_scope.py`
(`master_visible(user_id)` = `own(user_id)` **или** `free_to_take()`), поэтому
список, доска, бейджи этапов (`/api/repairs/stage-counts`), сводка по деньгам и
карточка клиента фильтруются одинаково и не разъезжаются.

**Клиенты подчиняются тому же правилу**: клиент виден мастеру, только если у
него есть доступные мастеру ремонты. Так работает список клиентов (`/clients` и
`/api/repairs/clients/list`), поиск по телефону
(`/api/repairs/clients/lookup`), автокомплит заказчика в приёмке
(`/web/clients-suggest`) и карточка клиента (`/clients/{id}` — без доступных
ремонтов отдаёт 404). Счётчик ремонтов у клиента считается только по доступным.
Приёмке это не мешает: клиент подбирается сервером по `phone_norm`
(`app/routers/repairs.py`, `_persist_repair`), а не по ответу поиска,
поэтому дубли не появляются.

Публичная страница статуса `/r/{token}` (и её JSON-вариант
`/api/public/r/{token}`) открывается без логина — доступом служит сам токен:
192 бита, `secrets.token_urlsafe(24)` (`app/services/numbering.py`),
перечислить его нельзя.

Права разделены на «смотреть» и «менять»:

- **смотреть** — `can_view_repair()`: свои и свободные ремонты (те же границы,
  что и у списка);
- **менять** — `can_access_repair()`: свои заказы (назначен напрямую или через
  `repair_masters`), у старших ролей — любые;
- **назначать исполнителей** — `can_assign_repair_masters(user, repair)`:
  администратор и оператор всегда; мастер — на свободный ремонт
  (`is_free_repair()`, берёт себе кнопкой «🙋 Взять себе» прямо в строке
  списка), на свой (добавляет напарников и помощников) или на свою приёмку,
  пока исполнитель не назначен. Занятый чужой заказ мастер себе не
  переписывает — в том числе чужую приёмку без исполнителя: она уже занята
  принявшим её мастером, поэтому «Взять себе» отвечает 403;
- **на приёмке** мастер выбирает исполнителем себя или оставляет поле пустым —
  тогда ремонт уходит в общую очередь;
- **этикетка своей приёмки печатается** — `can_print()` разрешает приёмщику
  бланк и этикетку, ПОКА исполнитель не назначен: автопечать при сохранении
  приёмки обязана работать (наклейку клеят на технику при клиенте). Как только
  заказ передали другому мастеру, печать у приёмщика закрывается;
- очередь печати `/print/jobs` мастеру — 403 (там PDF с чужими персональными
  данными).

Из вкладки убраны быстрые фильтры-этапы, заголовок «Все ремонты / Реестр по
этапам» и подсказка про двойной клик; добавлена колонка «🛠 Что починили»
(поле `work_done` — что сделали, со слов мастера; оно же печатается в бланке).

В выпадающем списке статусов, кроме пяти статусов, есть два **состояния** —
это факты из дат и оплаты, а не строки статуса (`webui/data.py`,
`EXTRA_STATUS_FILTERS`):

| Пункт фильтра | Что отбирает |
| --- | --- |
| «✓ Готово, стоит в сервисе» | `status = «Завершён»` и `issued_at` пустой |
| «⚠ Выдано, но не оплачено» | `issued_at` заполнен и `paid = false` |

Доска ремонтов (`/repairs?view=board`) — один общий список карточек активных
ремонтов от новых к старым: колонок по этапам на ней нет, этап виден в чипе
статуса на карточке.

Доставка отмечается кнопкой «Доставка» в приёмке (`is_delivery`): район
обязательный, комментарий — нет (`delivery_comment`). Без этого окна заказ
считается принятым лично в сервисе. Потом её можно поправить чипом «Доставка»
в паспорте карточки (`POST /repairs/{id}/delivery`, только старшие роли):
там же вписывается телефон доставщика (`delivery_courier_phone`).

В паспорте карточки есть три чипа, которые открывают окно со списком по
двойному клику (на телефоне — одним касанием): «Состояние»
(`condition_notes`, список отметок `CONDITION_OPTIONS` + свой текст),
«Комплектация» (`complectation`, список из `DEFAULT_COMPLECTATION` и
справочника `complectation_items`) и «Доставка». Чип «Статус» стоит в конце
блока. Клик по имени мастера открывает меню действий — передать ремонт,
назначить мастером, назначить помощником, убрать с ремонта
(`POST /repairs/{id}/master-action`).

Поиск в «Все ремонты» (`?q=`) учитывает номер ремонта и серийник — их читают с
этикетки на технике (раньше в условии не было `Repair.number`, и поиск по номеру
не работал).

Последняя колонка таблицы («🏁 Итог») — **остаток после расходов**: сумма
ремонта минус запчасти и выплаты мастерам, по той же формуле, что плитка
«Общая прибыль» над таблицей; отрицательный остаток показывается красным.

## Конструктор блоков (порядок страницы — личный)

Админ может переставить под себя и блоки страницы, и колонки таблицы.
Конструктор **свёрнут**: на **карточке ремонта** и во вкладке **«Все ремонты»**
справа над контентом лежит одна кнопка-пилюля **«🧩 Конструктор»**. По нажатию
раскрывается панель с двумя режимами — **«Блоки страницы»** и **«Колонки
таблицы»** (второй только в списке), подсказкой по активному режиму и кнопками
**«💾 Сохранить»** / **«↺ По умолчанию»**; крестик ✕ сворачивает панель и
гасит режим правки. Режимы не смешиваются: включение одного выключает другой.

В режиме правки у каждого блока появляется компактная строка с названием и
стрелками ↑ ↓, у каждого заголовка колонки — ручки ← →; и то и другое можно
тянуть мышью.

Порядок хранится в таблице `user_page_layouts` (одна строка на
`user_id + page`), поэтому раскладка **личная**: у второго админа она своя, а
мастер и оператор видят порядок по умолчанию и кнопки конструктора не видят
(`POST /ui/layout` без роли `admin` отвечает 403).

Блоки карточки: `hero` (шапка с номером), `passport`, `fault` (неисправность и
мастера), `parts`, `pay`, `log`. Блоки списка: `toolbar` (поиск и фильтры),
`legend`, `bulk` (массовые действия), `table`, `pager`. Колонки таблицы
(`page="repairs_columns"`): `bulk`, `date`, `device`, `accepted`, `fault`,
`fixed`, `sum`, `parts`, `client`, `masters`, `payout`, `total`, `actions`.

Технически: в шаблонах блоки помечены `data-block="<имя>"`, маршрут
`app/webui/routes_repairs.py` кладёт в контекст `layout` (`{блок: index}`), а
шаблон печатает `style="order:N"`. Порядок применяется CSS-свойством `order`,
поэтому разметку переставлять не нужно; блоки карточки лежат прямо в
`.rcard` (двухколоночный grid, `.is-wide` — во всю ширину).

Колонки — иначе: в таблице CSS `order` не работает, поэтому `layout.js`
переставляет ячейки по-настоящему — заголовки в `<thead>` и все `<td>` с тем
же `data-col` в каждой строке `<tbody>`. Порядок приходит из атрибута
`data-col-order` на `<table>`, а сам скрипт подключён сразу после таблицы,
чтобы колонки встали на место до первой отрисовки. Инлайн-редактирование
ячеек привязано к `data-edit`, а не к номеру колонки, поэтому перестановка его
не ломает.

Логика — `app/webui/layout.py`: `normalize()` отбрасывает чужие имена и
дописывает в конец новые блоки, поэтому после обновления страницы сохранённая
раскладка не ломается и не «съедает» свежие блоки. Тест
`tests/test_page_layout.py::test_layout_js_moves_columns_and_their_cells`
прогоняет сам `layout.js` в jsdom и проверяет, что шапка и каждая строка
встали в сохранённый порядок, а `test_panel_opens_and_switches_modes` — что
панель стартует свёрнутой, раскрывается по кнопке, переключает режимы и
сворачивается обратно (без node/jsdom тесты честно пропускаются).

### Номер телефона: +993, код оператора и 6 цифр

Номер на приёмке принимается только в туркменском формате: **+993 + код
оператора + 6 цифр**. Допустимые коды: **12, 60, 61, 62, 63, 64, 65, 71, 72**
(`TM_OPERATOR_CODES` в `app/services/numbering.py`).

- Префикс `+993` уже стоит в поле «Номер телефона» и не стирается
  backspace'ом; в необязательные поля (второй контакт, дополнительные номера)
  он подставляется при первом касании.
- Пока номер не совпал с правилом, под полем горит подсказка: неверный код
  («Неверный код оператора «66». Допустимые коды: …»), не хватает цифр
  («…нужно ещё 2 цифр(ы) — всего 6 цифр») или лишние цифры. Отправить форму с
  таким номером нельзя.
- Правило повторяется на сервере (`validate_tm_phone()` в
  `POST /repairs/new`): форма помечена `novalidate`, а отправить её можно и в
  обход скрипта. Ошибка возвращается текстом в ту же форму (400).
- Проверка касается только приёмки. В API (`POST /api/repairs`) и в правке
  клиента по-прежнему проходят любые номера — там есть zahraniжные.
- Короткие местные варианты («8 61 234567», «61 234567») тоже принимаются:
  `normalize_phone()` приводит их к тому же `99361234567`.

## Приёмка: конфликты и удалённые клиенты

Номер ремонта (`{TYPE}-{CITY}-{YYYY}-{NNNNN}`) выделяется по максимальному
существующему, поэтому при одновременной приёмке двумя операторами возможен
конфликт уникального индекса — запрос повторяется (до 5 раз) с новым номером.

Два правила, которые держат этот повтор рабочим:

- **Классификация конфликта** (`app/db/conflicts.py`): повторять имеет смысл
  только конфликт номера ремонта. Если база отклонила запись из-за телефона
  клиента (`ix_clients_phone_norm`) или по другой причине, оператор получает
  честный текст ошибки, а в логе видно имя ограничения — раньше любой
  `IntegrityError` показывался как «Не удалось выделить номер ремонта».
- **Удалённый клиент не блокирует приёмку.** Удаление клиента мягкое
  (`deleted_at`), а индекс `phone_norm` уникальный без оговорок, поэтому поиск
  клиента при приёмке смотрит и удалённые записи: карточка восстанавливается
  (`deleted_at = NULL`), история её ремонтов сохраняется, действие пишется в
  аудит как `client.restore`. Имя при этом не перезаписывается молча —
  расхождение фиксируется в аудите (`client.merge_blocked`).

В повтор также передаются простые значения (`user_id`, `city_slug`), а не
ORM-объекты: `rollback()` делает объекты сессии «протухшими», и чтение их
атрибутов в async-коде падало с `MissingGreenlet` — то есть повтор номера не
работал вовсе.

## SMS-уведомления

Готовность ремонта отправляется клиенту SMS через внешний шлюз. Credentials —
только из окружения (`.env` / `deploy/env.production`):

```ini
SMS_GATEWAY_URL=https://sms.example.tm/api/send
SMS_GATEWAY_USERNAME=login
SMS_GATEWAY_PASSWORD=secret
SMS_VERIFY_SSL=true
```

Без `SMS_GATEWAY_URL` отправка отключена: API честно возвращает ошибку
(«SMS-шлюз не настроен»), а не делает вид, что сообщение ушло. Шаблоны текста и
тестовая отправка — в админке (`Админ → SMS`).

### Ежедневные напоминания «заберите технику»

Как только ремонт переведён в **«Завершён»** (кнопка «Ремонт закончен» или смена
статуса), клиенту раз в сутки уходит SMS с просьбой забрать технику — пока
технику не выдадут клиенту. Стандартный текст (правится в `Админ → SMS`, ключ
`pickup_reminder`):

> Уважаемый клиент, просим забрать вашу технику из нашего сервиса MERYOSAB.
> Находимся по адресу: Парахат 3/2, ж14.

Доступные плейсхолдеры: `{client_name}` `{number}` `{device}` `{days}`
`{ready_date}`. Пустой текст = текст по умолчанию.

Как это устроено:

| Что | Значение |
|---|---|
| Первое напоминание | через `REMINDER_FIRST_DELAY_HOURS` (24 ч) после готовности — в день готовности клиент уже получил SMS «ремонт готов» |
| Периодичность | `REMINDER_EVERY_HOURS` (24 ч), т.е. каждый день |
| Статусы в рассылке | «Завершён» и техника ещё не выдана (`issued_at` пустой) |
| Когда прекращается | техника выдана клиенту (кнопка «Выдано клиенту» → `issued_at`) или `REMINDER_MAX_COUNT`, если задан |
| Тихие часы | `REMINDER_SEND_FROM_HOUR`–`REMINDER_SEND_TO_HOUR` в `REMINDER_TIMEZONE` (по умолчанию 09:00–20:00 Ашхабад) |
| Проверка очереди | фоновая задача каждые `REMINDER_CHECK_INTERVAL_MIN` минут (15) |
| Выключить совсем | `REMINDER_ENABLED=false` |

Надёжность: напоминание отправляется **ровно один раз** — перед отправкой строка
ремонта «заявляется» условным `UPDATE ... WHERE reminder_next_at = <прежнее>`,
поэтому несколько воркеров не продублируют SMS. Если шлюз не ответил, попытка
повторяется через час и не считается отправленной; при выключенном шлюзе
очередь не «сгорает» — напоминания уйдут после включения.

Каждое напоминание пишется в историю ремонта (событие `notify`) и видно:
- в карточке ремонта — чип «🔔 N · след. дата»;
- в `Админ → SMS → Очередь напоминаний` (кто ждёт, сколько отправлено, когда
  следующее) с кнопкой «▶ Прогнать сейчас» — ручной запуск рассылки.

## AI (Итерация 6)

AI идёт за абстракцией `app/services/ai.py`: `predict_eta()` и
`weekly_summary()`. По умолчанию (без ключа) работает **честный статистический
фолбэк** — медиана срока по истории, с явным `source: stats`. Если в `.env`
заданы `AI_API_KEY` + `AI_BASE_URL` + `AI_MODEL` (OpenAI-совместимый API),
вызывается внешняя модель. Анти-галлюцинация: при `n < 3` возвращается
`«мало данных»`, ничего не выдумывается. Каждый вызов пишется в `ai_runs`
(аудит промптов/ответов).

**Редактор шаблона бланка** — в админке (`/admin/print-templates`). Бланк
управляется шаблоном из БД (`print_templates`): название сервиса, заголовок,
подзаголовок, набор полей (клиент/телефон/техника/серийник/комплект/неисправность/
принял/мастер/хранение/срок), юртекст, футер, формат A4/A5, подписи, **раскладка
экземпляров** (по 1 на странице / **2 на одном листе с линией разреза**) и
количество копий. Кнопка «Превью» рендерит PDF. Юртекст «хранение 3 месяца»
по умолчанию берётся из `settings` (не зашит в код).

## Резервная копия: экспорт и импорт данных

Админка → **Настройки → 💾 Данные** (`/admin/settings?section=backup`) или
JSON-API `/api/admin/backup/*` (только роль `admin`). Реализация —
`app/services/backup.py`, тесты — `tests/test_backup.py`.

**Экспорт** отдаёт архив:

```
msb_backup_2026-09-23_120000.zip
├── meta.json          дата, кто выгрузил, число записей по таблицам
├── msb_export.json    {"version": "1.0", "exported_at": "...", "tables": {...}}
└── media/…            файлы фотографий (только при ?media=1 / «Скачать с фотографиями»)
```

Таблицы в `msb_export.json`: `clients`, `repairs`, `repair_masters`,
`repair_parts`, `repair_history`, `repair_number_aliases`, `donor_units`,
`donor_parts`, `app_settings`, `sms_log`, `print_log` + служебные
(`users`, `cities`, `branches`, `payments`, `repair_part_orders`, `parts`,
`price_items`, `equipment`). Деньги — целые копейки в полях `*_cents`
(500 ман = `50000`), даты — `YYYY-MM-DD HH:MM:SS` (UTC), JSON-поля — строки
(`equipment_json`, `condition_json`, `details_json`…).

**Импорт** принимает тот же архив либо голый `msb_export.json` / `data.json`
и понимает выгрузку старой базы: `name` или `full_name`, `category` или
`device_type`, `serial_number` или `serial`, `equipment_json` или
`complectation`, строковые id `c-100` / `r-200`, числовые id сотрудников
(сопоставляются по имени, неизвестные мастера создаются выключенными).
Старые статусы («Выдано», «Готово к выдаче»…) переводятся в актуальные пять;
`paid_cents` без платежей превращается в один платёж; `warranty_until`
пересчитывается в текст гарантии; старые номера из `repair_number_aliases`
работают в переходе `/repairs/by-number/<старый номер>`.

Режимы: **merge** (по умолчанию) — записи сопоставляются по UUID, номеру
ремонта, телефону клиента и т.д., повторный импорт того же файла ничего не
дублирует; **replace** — сначала удаляются клиенты, ремонты (история,
платежи, фото, запчасти) и склад разбора, затем загружается файл; в
веб-форме требуется ввести слово `ЗАМЕНИТЬ`. Импорт идёт одной транзакцией:
ошибка откатывает всё. Настройки `ip_control` и `data_migrations` из файла
не применяются (чтобы чужой белый список не заблокировал администратора).
Обе операции пишутся в журнал аудита (`data.export` / `data.import`).
Полная спецификация полей — **`docs/EXPORT_FORMAT.md`**.

## Роли и безопасность

- Роли: `admin | manager | operator | master | callcenter`.
- Единая матрица прав «роль × операция» — `apps/api/app/core/permissions.py`:
  касса и финансовые поля (`price_final`, `cost_amount`, `master_payout`, `paid`)
  доступны только старшим ролям, мастер не может провести платёж или выписать
  себе выплату; назначать мастеров и закрывать ремонт могут admin/operator.
- Паспорт техники (`brand`/`model`/`serial`) принятый ремонт правится тоже только
  старшими ролями (`can_edit_device_info`): опечатку в марке исправляет оператор,
  мастер — нет. Марка не может стать пустой, каждое изменение пишется в историю
  ремонта (событие `device` со значениями «до → после») и в `audit_log`.
- Каждый endpoint проверяет роль (`require_roles`); админка — только admin.
- Публичная страница отдаёт только публичные поля (без диагноза мастера,
  себестоимости и телефона клиента).
- `public_token` — 128+ бит криптослучайный, не перебираемый.
- Аудит изменений цены/статуса/печати/удалений/ролей — в `repair_events` и
  `audit_log` (`GET /api/admin/audit`, только admin).
- Веб-интерфейс не хранит пароль: access-токен в httpOnly-cookie `msb_access`.
- Секреты (`SECRET_KEY`, `SMS_GATEWAY_PASSWORD`) — только из окружения,
  в коде и в репозитории их нет; `deploy/env.production` не коммитится.
- Согласие на ПДн и на хранение фиксируется в `clients.consent_*_at`;
  для 152-ФЗ заложено поле `clients.deleted_at` (процедура удаления).

## Roadmap (итерации)

- [x] **0 — Фундамент**: монорепо, Docker, Postgres, auth (JWT+роли), модели,
      админка (юзеры/города/точки), README, .env.example
- [x] **1 — Чат**: каналы, сообщения, realtime WS, упоминание ремонта, уведомления
- [x] **2 — Приёмка + печать**: форма приёмки (клиент → техника/комплект →
      фото/мастер/ETA → подтверждение), создание Repair+Client, номер, QR-token,
      фото с камеры (multipart → /media), PDF-бланк + print-agent, «Повторить
      печать», карточка ремонта с timeline/комментариями, **редактор шаблона бланка**
- [x] **3 — Публичная QR-страница**: статус + прогресс, техника/комплект, даты,
      «хранение 3 мес», «как обычно» (обезличенная статистика), контакты, noindex + rate-limit
- [x] **4 — Доска ремонтов + роли**: канбан со статусами/фильтрами/сменой статуса,
      очередь call-центра (согласовать / готово / просрочка), мастера видят только своё
- [x] **5 — Прайс API**: справочник цен (тип/бренд/неисправность/город), вилка
      `от–до`, срок, подсказка в форме приёмки, CRUD в админке (admin/manager)
- [x] **6 — Дашборд статистики + AI**: плитки «курс ремонта» (срок/чек/p90/SLA/загрузка
      мастеров), AI-прогноз ETA с анти-галлюцинацией (`n < порога` → «мало данных»),
      weekly-summary
- [x] **7 — Склад запчастей**: каталог (название/SKU/категория/остатки/цены/поставщик),
      привязка к ремонту (списание остатков, события в timeline), low-stock в дашборде
- [x] **8 — Оплаты / касса**: платежи по ремонту (сумма/метод cash|card|transfer),
      остаток, отмена платежа (admin/manager), выручка (всего/30 дней) в дашборде
- [x] **Админка: пользователи**: CRUD сотрудников (создание/редактирование/роль/пароль/
      отключение), защита от дублей email и отключения самого себя
- [x] **Поток «мастер → оператор»**: мастер принимает заявку (автоназначение исполнителя),
      печать **2 экземпляров договора** (клиент + сервис, с подписями), оператор оформляет
      починку — **расходы + цена + отметка оплачено**, статистика с **прибылью** (выручка − расходы)
- [x] **Туркменский регион**: Ашхабад (Asia/Ashgabat), +993, валюта **TMT (ман.)** во всех ценах
- [x] **Правка техники после приёмки**: марка/модель/серийник меняются в карточке
      (✏️ у строки техники) без пересоздания ремонта — номер, этикетка и история
      остаются; след в timeline и аудите, мастерам недоступно
- [x] **Компактная таблица «Все ремонты»**: короткие заголовки колонок
      (`📅 Дата`, `📺 Техника`, `🧾 Принял`, `🔧 Причина`, `💵 Сумма`, `🔩 Запчасти`,
      `👤 Клиент`, `👷 Мастера`, `💰 Выплата`, `🏁 Итог`) + кнопка-пояснение `?`
      у каждой колонки; в «Итог» добавлен бейдж оплаты
- [x] **Тесты**: 186 pytest-тестов (auth/чат/ремонты/прайс/склад/оплаты/админ/
      статистика/AI/печать/SMS/напоминания/правка техники/конфликты приёмки
      + 39 регрессионных на исправленные дефекты — `apps/api/tests/test_fixed_defects.py`)
- [x] **Аудит и исправления**: матрица прав, аудит действий, нормализация
      телефонов, идемпотентная приёмка с retry нумерации, валидация статусов,
      оверлейное боковое меню и облегчённая карточка ремонта

Подробное ТЗ, ER-модель, wireframes и риски — в `docs/msb-kickoff.md`.
