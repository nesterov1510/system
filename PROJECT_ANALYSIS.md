## 1. Резюме

**MSB** — собственная (без Bitrix/amoCRM/1С) система приёмки и ремонта техники для
сервисного центра в Туркменистане (Ашхабад, валюта TMT, телефоны +993).

Проект **рабочий и зрелый для MVP**: я проверил его вживую — 88 pytest-тестов
проходят, TypeScript компилируется без ошибок, production-сборка Next.js успешна,
полный E2E-цикл «приёмка → генерация PDF-бланка → публичная QR-страница» отрабатывает.

| Метрика | Значение |
|---|---|
| Python (backend + print-agent) | ~9 740 строк |
| TypeScript/TSX (frontend) | ~8 330 строк |
| Документация | ~2 130 строк (5 файлов) |
| API endpoints | 74 пути / 98 операций |
| ORM-моделей | 22 таблицы |
| Тестов | 88 (все проходят, 11.7 с) |
| Страниц UI | 17 маршрутов |

**Главный вывод:** архитектура и качество кода — хорошие, но есть **5 критичных
проблем** (утёкшие в репозиторий боевые SMS-креденшелы, пароль в localStorage,
дыра в правах мастера, порча данных клиентов, потеря фото в Docker) и системная
проблема **рассинхрона «Россия → Туркменистан»**: проект переименовали под новый
регион, но часть бизнес-логики осталась русской.

## 2. Архитектура

```
apps/api           FastAPI (Python 3.11), SQLAlchemy 2.0 async, JWT
apps/web           Next.js 14 App Router (PWA), Tailwind, без внешних UI-библиотек
apps/print-agent   Автономный поллер очереди печати (Linux/CUPS, Windows/SumatraPDF, raw IPP)
packages/shared    Константы статусов/ролей  ← МЁРТВЫЙ КОД (см. §6.2)
deploy/            systemd-юниты, env.production, update.sh
docs/              kickoff-ТЗ (ER-модель, API-draft, wireframes)
```

**Поток данных:**

```
Браузер (PWA) ──same-origin──> Next.js rewrites ──> FastAPI :8085 ──> PostgreSQL/SQLite
                                     │                    │
                                     └── /ws (WebSocket)  ├── ReportLab → PDF (бланк A4 / этикетка 58×38)
                                                          └── print_jobs(queued)
                                                                  │
                                              print-agent (poll 3 с) → lp / IPP / SumatraPDF
```

Ключевое удачное решение: фронтенд проксирует `/api`, `/ws`, `/media`, `/docs`
через `next.config.mjs`, поэтому браузеру не нужен CORS и не нужен прямой доступ
к backend — развёртывание в LAN работает «из коробки».

## 4. Сильные стороны

1. **Честная anti-hallucination стратегия в AI.** `services/ai.py` без API-ключа
   не выдумывает прогноз, а считает медиану по истории и возвращает
   `source: "stats"`, `confidence`, `n`, либо прямо `"мало данных"` при `n < 3`.
   Каждый прогон логируется в `ai_runs`.
2. **Печать data-driven, а не захардкожена.** Шаблон бланка лежит в БД
   (`print_templates`), редактируется из админки, есть preview-эндпоинт.
   `normalize_template()` отфильтровывает неизвестные поля и вычищает legacy-строки.
3. **print-agent — на удивление надёжный.** Три режима печати, сырой IPP-клиент
   на сокетах (обходит HTTP 426 у Epson), авто-fallback на единственный принтер
   в CUPS, PDF **всегда** сохраняется в `printed/` как запасной вариант,
   переавторизация по 401.
4. **Взрослые systemd-юниты:** `NoNewPrivileges`, `ProtectSystem=full`,
   `PrivateTmp`, `UMask=0027`, `Restart=on-failure`, осознанный `--workers 1`
   с комментарием про гонку при seed.
5. **`deploy/update.sh`** — образцовый: собирает от владельца каталога (`runuser`),
   чтобы файлы не стали root-овыми; при падении сборки **не** перезапускает web;
   в конце делает health-check и даже проверяет наличие свежего чекбокса в HTML.
6. **Защита от слабого пароля в prod:** `seed.py` бросает `RuntimeError`, если
   `ENV=prod` и `SEED_ADMIN_PASSWORD` пустой / `CHANGE_ME*` / `admin123`.
7. **Продуманная доменная модель:** несколько мастеров + помощники
   (`repair_masters.kind`), ручные vs складские запчасти (`is_manual` — чтобы не
   возвращать на остаток то, чего на складе не было), soft-delete для клиентов,
   запчастей и техники, `phone_norm` как уникальный ключ клиента.
8. **Идемпотентный seed** — безопасно перезапускается, не плодит дублей.
9. **Осознанные комментарии о технических ловушках.** Например в `models.py`
   объяснено, почему `Mutable.as_mutable()` нельзя переиспользовать между
   колонками; в `repairs.py` — почему связи мастеров переиспользуются, а не
   DELETE+INSERT (ломается уникальный индекс в одном flush).
10. **Ноль сторонних UI-зависимостей** во фронтенде (только next/react) →
    маленький бандл и нетサプライз-цепочек.

### 🔴 P0 — Критичные (безопасность)

#### 5.1 Боевые SMS-креденшелы закоммичены в репозиторий
`apps/api/app/core/config.py:56-60`

```python
SMS_GATEWAY_URL: str = "https://192.168.8.81/api/3rdparty/v1/messages"
SMS_GATEWAY_USERNAME: str = "KJV7XJ"
SMS_GATEWAY_PASSWORD: str = "fbsybvpoothupl"
SMS_VERIFY_SSL: bool = False
```

Это **не** плейсхолдеры вроде `CHANGE_ME` — это реальные логин/пароль рабочего
шлюза. Они попадают в любой клон репозитория и в git-историю навсегда.
Дополнительно `SMS_VERIFY_SSL=False` отключает проверку сертификата.

Прямое противоречие собственному `.env.example`: *«Секреты живут ТОЛЬКО в env.
Никогда не коммитьте реальный .env»* и комментарию в `services/sms.py`, что
дефолты в config — «только запасной fallback для окружений без БД».

**Фикс:** обнулить дефолты (`""`), credential-ы брать только из `Setting["sms_server"]`
или env; пароль в боевом шлюзе считать скомпрометированным и **ротировать**;
историю git — чистить (`git filter-repo`) или принять решение о ротации как
достаточной мере.

#### 5.2 Пароль пользователя хранится в localStorage
`apps/web/lib/api.ts:255-284`, используется в `apps/web/app/login/page.tsx:51`

Функция «Запомнить вход» кладёт **пароль открытым текстом**, обёрнутым в base64:

```ts
/** base64 (utf-8 safe) — это НЕ шифрование, только чтобы пароль
 *  не лежал в localStorage открытым текстом при беглом взгляде. */
```

Комментарий честно признаёт, что это не шифрование. На общем терминале
приёмки любой следующий сотрудник декодирует пароль одной командой в DevTools.
Любой XSS уводит креденшелы полностью, а не только сессию.

**Фикс:** убрать хранение пароля; «запомнить» = хранить email + использовать
`refresh_token` в httpOnly-cookie с тихим refresh (это и есть «production-путь»,
который сам код упоминает в комментарии на 2-й строке).

#### 5.3 Мастер может сам назначить себе выплату и провести платёж
`apps/api/app/routers/parts.py:138,225`, `apps/api/app/routers/payments.py:28`

**Проверено экспериментально** (пользователь только с ролью `master`, назначенный
на ремонт):

| Действие мастера | Ответ API | Ожидание |
|---|---|---|
| `POST /repairs/{id}/parts` (списывает 5 шт. со склада) | **201** | 403 |
| `POST /repairs/{id}/payments` (проводит 5000 наличными) | **201** | 403 |
| `PATCH /repairs/{id}` c `price_final: 99999, master_payout: 99999` | **200** | 403 |
| `POST /parts` (создать позицию каталога) | 403 ✅ | 403 |

`_can_access()` в `repairs.py:57` проверяет *принадлежность* ремонта, но не
*тип операции*. В результате мастер, которому дали доступ к своей карточке,
получает полный контроль над деньгами по ней: может завысить цену,
выписать себе выплату и «оприходовать» платёж. Каталог запчастей при этом
защищён правильно (`CanEditParts`) — то есть защита есть, но расставлена
несимметрично.

**Фикс:** ввести явную матрицу «роль × операция». Финансовые поля
(`price_final`, `cost_amount`, `master_payout`, `paid`) и платежи — только
admin/manager/operator. Списывать запчасти — master может только на **своём**
ремонте и, желательно, без права менять цену.

#### 5.4 WebSocket принимает refresh-токен
`apps/api/app/routers/ws.py:21-26`

```python
payload = decode_token(token)          # подпись проверена...
user_id = uuid.UUID(payload["sub"])    # ...но payload["type"] — НЕТ
```

REST-слой тип проверяет (`deps.py:36`: `if payload.get("type") != "access"`),
а WS — нет. **Проверено:** подключение с refresh-токеном возвращает
`{"type":"hello"}` вместо закрытия с кодом 4401.

Плюс `uuid.UUID(payload["sub"])` бросит `KeyError`/`ValueError` на токене без
`sub` (необработанное исключение в WS-хендлере).

**Фикс:** та же проверка `type == "access"`, что и в `deps.get_current_user`,
+ проверка `user.active` (сейчас есть, ок) + обёртка в try/except.

#### 5.5 В Docker-развёртывании фотографии теряются при перезапуске
`docker-compose.yml:22-35`

У сервиса `api` **нет ни одного volume**. При `STORAGE_MODE=local` (дефолт)
загруженные фото ремонта пишутся в `./uploads` **внутри контейнера**. Любой
`docker compose up -d --build`, рестарт или пересоздание контейнера — и все
фотографии принятых устройств исчезают. Для системы, где фото состояния
техники — юридически значимое доказательство при споре с клиентом, это критично.

Дополнительно в том же файле: PostgreSQL проброшен наружу (`ports: "5432:5432"`)
с паролем по умолчанию `msb`, у `api`/`web` нет `restart:` и healthcheck'ов.

**Фикс:** `volumes: - uploads:/app/uploads` (+ именованный том), убрать
`5432` из `ports` или повесить на `127.0.0.1:5432:5432`, добавить
`restart: unless-stopped`.

### 🟠 P1 — Высокие (порча данных и бизнес-логика)

#### 5.6 `normalize_phone()` всё ещё русская — дубли клиентов
`apps/api/app/services/numbering.py:57-64`

```python
# Strip leading country code 8/7 -> canonical 10-digit Russian number.
if digits.startswith("8") and len(digits) == 11: digits = digits[1:]
elif digits.startswith("7") and len(digits) == 11: digits = digits[1:]
```

Проект заявлен как туркменский (+993), а нормализация — под российские коды
7/8. Фронтенд при этом нормализует правильно (`apps/web/lib/phone.ts:31`):
локальный формат `8 XX XXXXXX` → `993XXXXXXXX`. **Бэкенд этого не делает.**

**Проверено:**

| Ввод оператора | `phone_norm` в БД |
|---|---|
| `+993 61 234567` | `99361234567` |
| `8 61 234567` (тот же номер, локальный формат) | `861234567` ❌ |
| `61234567` (без кода) | `61234567` ❌ |

Один человек, три разных `phone_norm` → **три записи в `clients`** с раздельной
историей ремонтов. Проверено через API: два ремонта на один номер в разных
форматах создали двух клиентов. Последствия: оператор не видит историю при
приёмке, клиенту уходят дубли SMS, статистика по уникальным клиентам
(`clients_unique` в `/repairs/stats`) завышена.

#### 5.7 Приёмка молча переименовывает существующего клиента
`apps/api/app/routers/repairs.py` (ветка upsert'а клиента в `create_repair`)

```python
else:
    client.full_name = payload.client.full_name
```

**Проверено:** клиент «Клиент А» с номером `+993 61 234567` после приёма

Типичные сценарии в реальности: семейный номер, корпоративный телефон,

**Фикс:** не перезаписывать имя; при несовпадении — показывать оператору

#### 5.8 Клиенты с нецифровым телефоном сливаются в одну запись
`Client.phone_norm` — `unique=True`; `ClientCreate.phone` — `Field(min_length=5)`

потому что upsert находит существующую запись с `phone_norm=""` и переиспользует её.

#### 5.11 Печать падает в 500 без шрифтов DejaVu
`apps/api/app/services/print.py:23-27`

